# Grilling 决策记录 — 零人工运维多 Agent 闭环系统（Q1–Q8）

> 目的：对 v1.0 PRD 做对抗式审查（Grilling），逐一带出"完整但不自洽"的承重墙级假设，逼问并锁定 8 项决策，最终落到 PRD v1.1。
> 用法：本文件是变更追溯；PRD §19 是精简版摘要，本文是完整论证。

## Q1 · 风险引擎是不是确定性规则？

**承重墙问题**：PRD 立论之一"风险等级不由 Agent 自评"，但原 §8.2 SK-10 是一个 LLM 驱动的 Skill，输出 `estimatedRiskLevel: L0-L4`，并注明"其输出仅作为风险引擎的输入"。若风险引擎是另一个 LLM，则"不由 Agent 自评"是空话——换个模型自评，依然可幻觉、可被提示注入带偏。最引以为傲的防线，地基是软的。

**原矛盾**：叙事（独立引擎裁决）与实现（SK-10 LLM 自评等级）自相矛盾。

**决策**：✅ **风险引擎 = 确定性规则查表（非 LLM）**。L0–L4 映射成声明式策略文件（动作动词 + 资源类型 + namespace 范围 + 冻结窗 → 等级）；Remediator 只提交动作，定级权在规则表，Agent 零覆盖权。SK-10 降级为"帮规则引擎把爆炸半径数据算清楚"，**不再自行下等级结论**。

**落点**：PRD §7.1 / §7.2 / §7.5、§8.2 SK-10、AG-03；R11 新增。

**可验证性**：红队可构造"看似安全实则高危"的动作，验证规则表仍判 L3/L4（而非依赖模型自觉）。

## Q2 · PolarDB-PG 与"纯开源自建栈 + 本地 Demo"矛盾

**承重墙问题**：用户选了"K8s + Prometheus 自建栈"，但 PRD §4.3 把阿里云托管库 PolarDB-PG 原样搬进架构；US-24（P0）要求"半小时一条 `docker compose up` 起 Demo"。PolarDB-PG 是托管库，塞不进本地 compose。

**原矛盾**：要么 Demo 跑不起来（打脸 US-24），要么用户被迫开云账号（违背纯开源叙事）。

**决策**：✅ **改为自托管 PostgreSQL + pgvector**（Apache/MIT，一条 compose 可起，向量+审计一张表）。PolarDB-PG 仅保留在 Later 路线图的"阿里云 Provider 适配"作为可选后端。

**落点**：PRD §4.3、§10、§16、US-24；对照检查表三·PolarDB-PG 行。

## Q3 · "Worker 不持凭证靠 Higress"未经证实

**承重墙问题**：立论"安全不靠 Prompt 靠架构"第一层是"真实密钥留在 Higress 网关"。但经核实（WebFetch Higress 仓库与 AI Gateway 文档），**Higress 是 API/LLM 网关，管不了 K8s 凭据、发不出 kubectl 令牌**——它代持的是模型 API Key、发的是 LLM consumer token。把它吹成"执行安全基石"是 overclaim，且可能是错误假设。

**原风险**：若这句不成立，L4 硬拦截、三层防御、整个安全叙事的承重墙都没了。

**决策**：✅ **拆成两个平面**：
- LLM/MCP 访问平面 → **Higress AI Gateway**（代持模型 API Key、发 consumer token、托管 MCP Server）
- K8s 执行凭据平面 → **独立 K8s 原生凭证 Broker**（持有真实集群高权凭据，按需 mint 短期、按 SA 最小化、单任务有效令牌；L3 须经人工审批后才发）

AgentTeams/Higress 只作为 Broker 的一种可能实现，而非安全模型唯一依托。

**净效果**：安全立论不仅未塌，反而更可证伪、可演示——执行安全是 K8s 原生的，红队可直接打 Broker。

**落点**：PRD §4.2（凭证安全行）、§4.3 治理层、§7.2 第一层、§9 k8s-mcp 鉴权、AG-03 权限范围；README 核心原则①、技术栈凭证安全。

## Q4 · 北极星指标能被"永远不执行"白嫖

**承重墙问题**：§14.1 预警"单看自主闭环率会诱导冒进"，§14.3 护栏却全单向（误修复/误抑制/二次故障）。但"最优解"是 Validator 永远判 FAIL、Remediator 永远不动——护栏全绿，闭环率≈0，系统退化成只会告警的摆设，却能在所有红线拿满分。

**原漏洞**：只说"要同看"，没定义阻止退化均衡的机制。

**决策**：✅ **对称护栏 + 可操作定义 + 固定基准**：
1. 新增**对称护栏"过度保守率/应执未执率"**（本可自主解决的 L1/L2 却升级人工的比例，红线 ≤15%），堵死"永远不执行"的退化策略；
2. 误修复/误抑制改**可客观自动判定**（误修复=修复后观察期 SLO 再劣化/触发回滚/引发二次故障；误抑制=被抑制告警中后续确认为真实故障的比例），不依赖主观；
3. 所有指标绑定**同一固定标注数据集**，单边优化无法刷分。

**落点**：PRD §14.1、§14.3（新增行）、§11.3；README 北极星指标行。

## Q5 · 复盘知识有没有回路回到系统

**承重墙问题**：标题"多 Agent 闭环"的"环"是否成立？原 Scribe 只写文档（SK-17 输出 Runbook PR），但没说这些产出如何回流——不回 RAG、不回规则表、不回根因定位。那闭环断在最后一环，是单向管道，系统不会越用越好。

**原风险**：与"知识沉淀""闭环"承诺矛盾；每次事故从零开始。

**决策**：✅ **定义显式反馈边**：Scribe 复盘产出经人工评审合并后，自动①入 RAG ②生成规则表候选补丁走变更审批 ③沉淀根因模式库给 Diagnostician 优先查。让"闭环"名副其实，"自主闭环率随时间提升"有机制支撑。

**落点**：PRD §5 AG-05（显式学习回路段）、§6.2⑧、§8.2 SK-17；对照检查表一·1.3⑧。

## Q6 · 确定性规则表怎么冷启动、未知动作怎么办、谁改表

**承重墙问题**：Q1 把风险引擎定为确定性规则表，但没解决：谁写初始 L0–L4 映射？表里没有的动作怎么办（默认放行=开后门；默认拒绝=啥也不干）？谁有权改表（若 Scribe 自动改，知识污染）？

**原风险**：空表则无自治覆盖；未知动作若默认放行则安全基石崩；若 Scribe 自动改表则越改越乱。

**决策**：✅ **种子规则集 + 未知动作默认拒绝 + 表变更人工治理**：
- 开箱内置覆盖常见 K8s 修复动词（scale/restart/rollout undo/cordon/drain/configmap edit/pvc delete 等）的 L0–L4 映射，Demo 首日即有真实自治覆盖；
- 表里没有的动作**一律默认拒绝并升级人工**（按 L3-equivalent 审批），但记录为候选补丁喂回 Q5 治理流；
- 规则表以声明式策略文件（Git）存储，变更走 **PR + 人工评审**，Scribe 候选只作输入、**绝不自动生效**。

**落点**：PRD §7.1（新增"未知"行）、§7.5（新增小节）、R11；§18 T-rule 对应。

## Q7 · 事件状态机靠 LLM 驱动还是代码驱动

**承重墙问题**：IncidentCommander（Manager）若实时判断推进状态机、做"裁决"，则①单点故障（崩溃/幻觉→整条闭环走偏且无兜底）②行为不确定（同事件两次不同路径，无法重放/审计）③"裁决"由 LLM 做本身就不可靠。

**原风险**：把整个闭环的可靠性押在一个会幻觉的模型上 = SPOF + 不可审计。

**决策**：✅ **代码引擎定编排 + LLM 仅做生成式子任务**：生命周期状态机与等级裁决由非 LLM 的确定性工作流引擎 + 规则表驱动（可审计、可重放、可回退）；LLM Manager 只做摘要、按结构化状态决定派工、起草给人看的描述。硬控制流不依赖 LLM 判断 → 消除 SPOF、行为可复现。

**落点**：PRD §4.1（图注）、§4.2 任务拆解/状态追踪行、§6.1（状态机注）、AG-00 职责与失败降级、§13 可靠性新增行。

## Q8 · "零人工运维"名实相符吗

**承重墙问题**：标题"零人工运维"沿用赛道方向名，但分级自治（L3/L4 必人工审批）+ Q6 未知动作默认拒绝升级——真正需要人的恰恰是重大事故。若读者预期"无人在环"，发现人在核心决策里，credibility 受冲击。

**原风险**：过度承诺；评委/用户读标题预期与正文现实不符。

**决策**：✅ **重写为"人类在环的自主运维闭环"**："零"指零日常重复性人力消耗（无人盯盘、无人工分诊告警风暴），而非零人类责任/零审批。重大事故仍由人拍板。与分级自治 + Q6 默认拒绝模型自洽。

**落点**：PRD 标题、§0、§1.3、§2.2（新增非目标"不宣称零人在环"）、§19；README 定位段。
