## 0. 一句话定义

> Argus 是一个开源的多 Agent 运维值班班组。它把「告警 → 根因 → 修复 → 验证 → 复盘」这条本该由人在凌晨三点完成的链路，交给一组职责分明、全程可审计、高风险动作必须请示人类的 AI Agent 来完成。

**关于"零人工运维"的诚实口径**：标题沿用业界方向名，但本系统的真实承诺是**「人类在环的自主运维闭环」**——"零"指**零日常重复性人力消耗**（无人盯盘、无人工分诊告警风暴），而非**零人类责任 / 零审批**。重大事故（L3/L4、未知动作）仍由人拍板。详见 §1.3 与 §2.2。

## 1. 背景与问题定义（Why）

### 1.1 现状痛点

零人工运维不是一个「AI 很酷所以来试试」的命题，它对应四个可量化的真实成本：

| 痛点 | 现状描述 | 量化影响（行业普遍水位） |
|---|---|---|
| **告警洪水** | 一次核心服务抖动触发上下游数十条告警，值班人先花 10 分钟判断「这是几起故障」 | 告警有效率普遍 < 5%，90% 以上告警无需人工动作；告警疲劳直接导致真实故障被漏看 |
| **根因定位靠人肉** | 排障依赖「谁经验最老」，在指标、日志、链路、变更记录四个系统间反复横跳 | MTTR 中 60%–70% 的时间消耗在定位而非修复 |
| **修复知识不沉淀** | 同类故障反复发生，Runbook 写完就过期，处置经验锁在个别老员工脑子里 | 重复性故障占比可达 40%；核心运维人员离职即知识断层 |
| **复盘是负担** | 事故复盘靠事后回忆拼时间线，写完归档无人再看 | 复盘产出无法反哺自动化，闭环断在最后一环 |

### 1.2 为什么是多 Agent，而不是单个大模型

这是本项目必须先回答清楚的问题，否则方案没有存在意义：

1. **职责边界即安全边界**。排障需要广泛读权限，修复需要收敛的写权限。单 Agent 意味着一套凭证既能读遍全集群又能改动生产 —— 这在企业环境不可接受。拆成多 Agent 后，权限可以按角色最小化授予。
2. **上下文污染问题**。告警降噪需要处理成百上千条低价值消息，根因分析需要深度推理。塞进同一个上下文窗口，噪声会淹没推理质量。分 Agent = 分上下文。
3. **验证者必须独立于执行者**。让写出修复方案的同一个 Agent 判断「修好了没有」，等同于让学生自己批卷子。恢复验证 Agent 必须是独立职能、独立证据源。
4. **失败可局部降级**。根因定位失败不应阻断告警聚合；执行 Agent 熔断不应影响复盘归档。单体架构做不到优雅降级。

### 1.3 项目边界前提

- 本项目**不做监控采集**，不重造 Prometheus/Loki，只做其上的决策与执行层。
- 本项目**不追求「无人化」的营销叙事**，追求的是「人的注意力从 100 起告警收敛到 3 起真正需要判断的决策」。
- **人类在环是设计前提，不是妥协**：L3/L4 高风险动作、未知动作、知识资产变更，必须有人参与决策或评审。系统对人做"副驾 + 守门"，而非"替代"。

## 2. 目标与非目标

### 2.1 产品目标（按优先级）

| # | 目标 | 可衡量结果（Demo 环境验收） |
|---|---|---|
| G1 | 把多源告警收敛为少量高置信度事件 | 告警降噪率 ≥ 90%，事件聚合准确率 ≥ 85% |
| G2 | 自动产出可信的根因结论与证据链 | 根因 Top-1 命中率 ≥ 60%，Top-3 ≥ 85%，每个结论必须附证据引用 |
| G3 | 在明确的安全边界内自动完成修复 | L1/L2 类故障自主闭环率 ≥ 70%，误修复率 ≤ 2% |
| G4 | 修复结果由独立 Agent 验证，不达标自动回滚 | 验证覆盖率 100%，回滚成功率 100% |
| G5 | 每起事故自动沉淀为可复用知识资产 | 复盘报告自动生成率 100%，知识蒸馏为 Runbook/Skill 的转化率 ≥ 30% |
| G6 | 全流程可审计、可追溯、可复现 | 每个动作有 Trace + 操作日志 + 变更快照，支持事后完整回放 |

### 2.2 非目标（Non-goals）— 明确不做什么

> 写清楚不做什么，比写清楚做什么更能防止范围蔓延。以下项在 v1.1 明确不做：

| 非目标 | 理由 |
|---|---|
| ❌ 不做监控数据采集与存储 | 复用现有 Prometheus/Loki 栈，避免与成熟方案竞争 |
| ❌ 不做告警规则的自动生成与调优 | 属于可观测治理领域，与本闭环正交，留待 v2 |
| ❌ 不做容量规划与成本优化 | 赛道方向二/三的范畴，避免摊薄核心叙事 |
| ❌ 不做安全事件响应（SOC/SIEM） | 安全事件的处置链路、合规要求与运维故障差异过大 |
| ❌ 不覆盖有状态服务的数据面修复 | 数据库主从切换、数据修复等动作风险过高，v1.0 一律划入 L4 禁止区 |
| ❌ 不做多云/混合云统一纳管 | v1.0 只保证 K8s + Prometheus 栈跑通，云厂商适配放到 Provider 扩展点 |
| ❌ 不做自研 LLM 或模型微调 | 使用开源/商用模型 API，通过 Higress 网关统一接入 |
| ❌ 不替代人工 On-Call 值班制度 | Argus 是值班人的副驾，L3 及以上决策权始终在人 |
| ❌ 不宣称"零人在环" | 高风险与未知动作必须人工审批/评审，"无人"是误导，本系统定位为"人类在环的自主闭环" |

## 3. 目标用户与核心场景

### 3.1 用户画像

| 角色 | 描述 | 核心诉求 | 对本系统的成功定义 |
|---|---|---|---|
| **On-Call SRE**（主用户） | 轮值工程师，凌晨被叫醒的人 | 别拿无关告警吵我；叫醒我时请把证据准备好 | 夜间被打断次数下降；被叫醒时 5 分钟内能做决策 |
| **SRE 负责人** | 团队管理者 | 团队 MTTR 下降、知识不依赖个人、变更可审计 | 有数据能证明团队效能提升；事故有完整审计链 |
| **业务研发** | 服务 Owner | 我的服务出问题要第一时间知道，最好已被处理 | 收到的是「已处理完毕 + 原因说明」而非「你的服务挂了」 |
| **平台/开源使用者** | 想复用本项目的团队 | 能在自己环境半小时跑起来；能替换成自己的工具链 | 一条命令起 Demo；Provider 层可插拔 |

### 3.2 五个核心场景（对应赛道方向一）

| 场景 | 输入 | 期望产出 | 覆盖 Agent |
|---|---|---|---|
| S1 多源告警聚合与降噪 | Alertmanager webhook、Loki 日志告警、K8s Event、探针失败、人工报障 | 1 个去重定级后的 Incident 对象 + 关联告警簇 | Sentinel |
| S2 自动根因定位 | Incident + 拓扑 + 指标 + 日志 + 变更记录 | 带置信度的根因假设链 + 证据引用 | Diagnostician |
| S3 修复建议生成与执行 | 根因结论 + Runbook 检索结果 | 分级修复方案 + 执行结果 + 变更快照 | Remediator（+ Human 审批） |
| S4 服务恢复验证 | 修复动作 + SLO 定义 | 验证通过 / 失败 → 触发回滚或升级 | Validator |
| S5 事故复盘与知识沉淀 | 全链路 Trace + 时间线 | 复盘报告 + 新增/更新的 Runbook 与 Skill + **规则表候选补丁** | Scribe |

## 4. 系统总体设计

### 4.1 Agent 编队（1 Manager + 5 Worker + 1 Human）

```
                        ┌──────────────────────────────┐
   多源告警 ───────────▶│  Sentinel  哨兵               │  归一化 · 聚类 · 降噪 · 定级
   (Alertmanager/Loki/  └──────────────┬───────────────┘
    K8s Event/探针/人工)               │ Incident 对象
                                       ▼
   ┌───────────────────────────────────────────────────────────────┐
   │        IncidentCommander  事件指挥官（Manager Agent）           │
   │   状态机推进* · 任务拆解 · 上下文分发 · 升级决策 · 熔断控制      │
   │   *注：状态机由确定性工作流引擎驱动，非 LLM 实时判断（见 §4.2） │
   └──┬──────────────┬──────────────┬──────────────┬──────────────┘
      │              │              │              │
      ▼              ▼              ▼              ▼
 ┌──────────┐  ┌───────────┐  ┌──────────┐  ┌──────────┐
 │Diagnos-  │  │Remediator │  │Validator │  │  Scribe  │
 │tician    │  │  执刀手    │  │  验收官   │  │  书记官   │
 │ 诊断官    │  │           │  │          │  │          │
 │根因定位   │  │方案+执行   │  │恢复验证   │  │复盘+沉淀  │
 └──────────┘  └─────┬─────┘  └────┬─────┘  └──────────┘
                     │  L3 高风险   │ 验证失败
                     ▼             ▼
              ┌─────────────────────────┐
              │  Human: OnCall  值班人   │  审批 · 纠偏 · 急停
              └─────────────────────────┘
```

**为什么是这 6 个角色**：严格对齐赛道方向一的五段闭环（聚合/根因/修复/验证/复盘），每段一个专职 Worker，外加一个负责编排与安全决策的 Manager。不多设角色（避免为凑数而拆），不少设（避免执行者兼任验证者）。

### 4.2 与 AgentTeams 框架能力的映射

> 赛道明确要求：「AgentTeams 不是只看是否提到工具名称，应重点核验角色编排、任务拆解、上下文传递、协同执行与状态追踪如何映射到框架能力。」以下是逐项映射：

**v1.4 修订（双部署模式）**：AgentTeams 支持两种部署模式，能力等价，按规模选择：

| 模式 | 适用场景 | 前置条件 | Agent 定义方式 | 示例微服务/K8s 资源 |
|---|---|---|---|---|
| **本地 Docker 模式** | Demo + 单机生产 | 仅 Docker + 2核4G | AgentTeams 安装脚本/Docker 配置定义 Worker（非 CRD） | 被监控集群用 kind 单独创建 |
| **K8s Helm 模式** | 共享/多租户生产 | K8s 集群 | `Worker`/`Team`/`Human` CRD 声明式 YAML | 同集群或跨集群 |

> 两种模式下 Agent Identity 的属性（职责、权限边界、协同关系）**语义等价**，只是声明载体不同。下表映射适用于两种模式，标注「CRD」处为 K8s 模式的声明方式，本地模式对应等价的 Docker 配置。

| 框架能力 | AgentTeams 提供的机制 | Argus 的具体落地 |
|---|---|---|
| **角色编排** | K8s 风格声明式 CRD：`Worker` / `Team` / `Human`（K8s 模式）；Docker 配置 + 安装脚本（本地模式） | 用 6 份配置定义值班班组：1 个 Manager、5 个 Worker、1 个 Human（OnCall）；K8s 模式用 `Team` CR 绑定为 `argus-crew`，本地模式用 AgentTeams 安装脚本定义。角色增删只改配置，不改代码 |
| **任务拆解** | Manager Agent 集中编排控制流，向 Worker 分派任务 | IncidentCommander 按事件状态机把一起事故拆为 7 段子任务：`triage → diagnose → plan → approve → execute → verify → review`，每段有明确的输入契约、超时和失败分支。**状态机由 Manager 内置的确定性编排模块（代码+配置）驱动，不依赖 LLM 实时判断**（Q10 修正/Q14/Q15）；Manager 是 OpenClaw Agent，确定性编排逻辑作为系统指令 + 确定性工具集（如 `advance-state`）存在，LLM 只做生成式子任务（摘要、描述）。**Manager 是编排真相源**，不引入外部编排引擎 |
| **上下文传递** | Matrix Room + `m.mentions`，无隐藏的 agent-to-agent 调用；MinIO 共享文件系统承载大对象 | **每起事故独占一个 Matrix Room**（`#incident-{id}`），所有 Agent 与值班人同处一室。结论、假设、决策以结构化消息在 room 内流转；火焰图、日志切片、pprof、YAML diff 等大件落 MinIO，room 内只传引用句柄，避免 token 爆炸 |
| **协同执行** | 三种 Runtime 共存（OpenClaw / QwenPaw / Hermes），可同房间混用 | 编排与工具调用类角色（Commander/Sentinel/Remediator）用 **OpenClaw**（技能生态丰富）；需要写临时分析脚本、跑数据处理的 Diagnostician 用 **Hermes**（终端沙箱 + 持久记忆）；轻量高频探针类任务用 **QwenPaw**（内存占用低 80%） |
| **状态追踪** | Manager heartbeat 在 Room 内可见；Controller reconcile metrics；AgentLoop 全栈可观测 | 自定义 `Incident` 对象承载状态机，**状态迁移由 Manager 内置确定性编排模块写入**（非外部引擎，Q10 修正）；每次迁移在 Room 内广播；全量状态迁移 + 输入参数写入 PostgreSQL append-only 审计表实现可重放（确定性逻辑 + 审计回放 = 可复现）；AgentLoop 记录 LLM 推理 / Skill 调用 / MCP 工具调用全链路 Trace |
| **凭证安全** | Worker 永不持有真实凭证，只带消费者令牌 | **拆分为两个平面（见 §7.2）**：① LLM/MCP 访问平面由 **Higress AI Gateway** 代持模型 API Key 并向 Agent 发短期 consumer token；② K8s **执行凭据平面由独立的 K8s 原生凭证 Broker** 持有，按需 mint 短期按 SA 最小化、单任务有效的令牌。Worker 结构性不持有真实集群凭据，即使被提示注入攻破，破坏上限由 Broker 侧策略 + RBAC 硬约束 |
| **人工介入** | `Human` CRD 建模人类为一等公民；人类可随时进入任意 Room 干预 | L3 审批以结构化卡片在 Room 内 @OnCall；人类可随时 `@commander 停止` 触发急停；所有人工干预自动进入复盘时间线 |
| **Skill 注册与分发** | Nacos Skills Registry + skills.sh 生态，Worker 按需拉取 | Argus 的 17 个 Skill 发布到 Nacos 私有注册表，支持版本化、灰度、回滚；通用能力同步开源到 skills.sh |
| **外部工具接入** | Worker/Team CRD 上的声明式 MCP 配置；Higress 托管 MCP Server | Prometheus / Loki / K8s / Git / 工单系统全部通过 MCP Server 接入，声明在 CRD 中 |

## 7. 分级自治与安全边界（核心章节）

> 这是整个方案最需要说清楚的部分。三条立论经 v1.1 Grilling 强化，均从"靠架构/规则"而非"靠模型/Prompt"出发：
> 1. **风险等级由确定性规则查表裁决，不由 Agent 自评，也不由另一个 LLM 二审**（防止"换模型自评"的软地基）；
> 2. **安全靠架构分层**：LLM/MCP 平面归 Higress，K8s 执行凭据归独立 Broker + RBAC + 规则表三层硬约束；
> 3. **执行者与验证者强制分离**，验证者独立取数且无权回滚。

### 7.1 L0–L4 风险分级模型

| 等级 | 定义 | 典型动作 | 执行策略 | 快照 | 审批 |
|---|---|---|---|---|---|
| **L0** 只读 | 不改变系统任何状态 | 查指标、看日志、`kubectl describe`、拓扑查询 | 全自动，无限制 | 否 | 否 |
| **L1** 低风险自愈 | 影响面单实例，系统可自愈，失败无残留 | 重启单个无状态 Pod、驱逐异常 Pod、清理临时文件、触发一次探针 | 全自动执行 + 事后通知 | 否 | 否 |
| **L2** 中风险 | 影响面服务级，可逆，有明确回滚路径 | HPA 上限内扩缩容、流量权重调整、限流/降级开关、ConfigMap 热更新、清理缓存 | 自动执行 + **强制变更前快照** + 实时通知 + 一键回滚 | **是** | 否 |
| **L3** 高风险 | 影响面跨服务或涉及发布态，回滚有代价 | 版本回滚、跨可用区流量切换、Deployment 镜像变更、Ingress 规则变更、批量重启 | **仅生成方案，必须人工审批后执行** | **是** | **是** |
| **L4** 禁止 | Agent 永不执行，只能生成建议供人操作 | 删除 PVC / Namespace / CRD、修改 RBAC 与密钥、数据库 DDL/DML、主从切换、扩容物理资源、跨集群操作、任何数据写删 | **Broker + 规则表硬拦截，Agent 无此权限** | — | 人工执行 |
| **未知** 表外动作 | 规则表中无匹配项的动作 | 任何未预定义的新动作 | **默认拒绝执行 + 升级人工**（记录为候选补丁喂回治理流，见 §7.5） | — | 人工裁决 |

### 7.2 三层防御纵深

安全不能只靠 Prompt。三层缺一不可：

| 层 | 机制 | 防的是什么 |
|---|---|---|
| **第一层：K8s 凭证 Broker（执行凭据平面）** | 真实集群高权凭据**只存在于 Broker**；任何 Agent（含 Higress）都拿不到。Remediator 执行写操作前，必须向 Broker 申请短期、按 SA 最小化、单任务有效的令牌；令牌发放受确定性规则表 + 人工审批双重约束；L4 与未知动作在 Broker 侧直接拒发令牌 | 防「Agent 被提示注入攻破后为所欲为」。这是唯一不依赖模型正确性的防线，且可红队直接验证 |
| **第二层：K8s RBAC 最小权限** | 每个 Agent 独立 ServiceAccount，权限按职责最小化；Diagnostician/Validator/Scribe 全部只读 | 防「某个 Agent 逻辑错误越权操作」 |
| **第三层：确定性风险分级引擎 + 审批流** | **声明式规则查表**对动作定级（L0–L4 + 未知默认拒绝），Agent 零覆盖权；L3 强制人工审批，L2 强制快照 | 防「方案本身是错的」或「Agent 自评风险过低」 |

> **v1.1 修订（凭证分层）**：原 PRD 将"Worker 不持真实凭证"全部押在 Higress 上。经核实，**Higress 是 API/LLM 网关，管不了 K8s 凭据、发不出 kubectl 令牌**。因此修正为：Higress 只管 **LLM/MCP 访问平面**（代持模型 API Key、发 consumer token、托管 MCP Server）；K8s **执行凭据由独立 Broker 持有**。原立论"安全靠架构不靠 Prompt"不仅未塌，反而更可证伪、可演示——执行安全是 K8s 原生的。

### 7.3 熔断与急停

| 触发条件 | 动作 |
|---|---|
| 同一 Incident 连续 2 次修复失败 | 熔断该事件的自动执行，回滚至初始快照，强制升级人工 |
| 15 分钟内自动执行动作数 > 阈值 | 全局限流，进入「只诊断不执行」模式 |
| 修复后 SLO 反而恶化 | 立即自动回滚 + 熔断 + P0 升级 |
| 处于变更冻结窗口（大促/发布窗口） | 仅允许 L1；L2 及以上全部转人工审批 |
| 人类在 Room 内发出急停指令 | 全流程立即停止，保持现场，等待人工接管 |
| 同一根因短时间重复出现 ≥ 3 次 | 判定为「自动修复无效」，停止重试，升级人工并标记为疑似深层问题 |

### 7.4 数据与隐私合规

| 风险点 | 处置 |
|---|---|
| 日志/Trace 可能含用户 PII | 入 LLM 上下文前强制脱敏（手机号/邮箱/身份证/银行卡/Token 正则 + 命名实体识别双重过滤）；AgentTeams 自带的 debug log 导出已内置 PII 脱敏，需扩展规则集 |
| 生产数据出境风险 | 支持全本地化部署（本地模型 + 本地向量库），敏感环境可完全断外网 |
| 凭证泄露 | Worker 层面结构性不持有真实集群凭据（Broker 代持）；令牌短期有效、定期轮转；所有令牌发放与执行强制审计 |
| 审计合规 | 全量操作日志不可篡改存储（append-only），保留期可配置，满足等保与内审要求 |
| 知识库越权 | 知识库按服务/团队做多租户隔离，Agent 检索受 RBAC 约束 |

### 7.5 风险规则表治理（v1.1 新增，v1.4 修订 Q9 两阶段管线）

确定性规则表是整个安全模型的基石，其生命周期必须被显式治理，否则要么 Demo 首日无自治覆盖，要么未知动作悄悄放行。

**v1.4 修订（两阶段管线）**：种子规则表中有 `max_replicas_affected`、`within_hpa_limits`、`must_trigger_rollout` 等约束需要运行时数据才能校验。Q1 的"确定性规则查表"定义为**两阶段管线**：
1. **第一阶段——静态匹配**：action_verb + resource_type + namespace_scope + freeze_window → 候选等级 + 约束列表（纯查表，不查集群状态）
2. **第二阶段——运行时约束校验**：查集群状态验证约束（如目标 Deployment 的副本数、HPA 配置上限、ConfigMap 引用关系），约束不满足则**向上取一级**（fail-safe 而非 fail-open）。SK-10（`blast-radius-eval`）是第二阶段的数据提供者——它算出爆炸半径数据喂给规则引擎，最终等级仍由确定性管线裁决，不是 LLM。

| 治理维度 | 方案 |
|---|---|
| **种子规则集** | 开箱内置覆盖常见 K8s 修复动词的 L0–L4 映射：`kubectl scale`/`rollout restart`/`rollout undo`/`cordon`/`drain`/`configmap edit`/`pvc delete`/`rbac 修改` 等，按"动作动词 + 目标资源类型 + namespace 范围 + 是否在冻结窗"映射到等级。**保证 Demo 首日即有真实自治覆盖**，而非空表起步 |
| **未知动作默认策略** | 规则表中无匹配项的动作 → **一律默认拒绝执行并升级人工**（按 L3-equivalent 审批）。绝不"默认放行"——那等于给 Q1 的确定性安全开后门。被拒动作记录为**候选补丁**喂回 §5 的治理流 |
| **规则表变更治理** | 规则表以声明式策略文件（Git 管理）存储，任何变更走 **PR + 人工评审**，Scribe 生成的候选只作输入、**绝不自动生效**。变更有版本、可回滚 |
| **冷启动** | 由种子集保证，无需从零积累；用户可在 `US-27` 支持的配置文件里按环境/服务/时段差异化覆盖 |
| **可审计** | 每次裁定可追溯到"命中了规则表的哪一条"，红队测试可构造"看似安全实则高危"的动作验证规则表仍判 L3/L4 |

### 8.2 核心 Skill 详细契约

> 以下按赛道要求的九要素展开。v1.4 已完成 8 个 Skill 契约（SK-01/02/07/09/10/12/14/17），其余 9 个在技术设计文档中同格式补全。

#### SK-01 · `alert-normalize` 告警归一化

| 要素 | 内容 |
|---|---|
| **用途** | 将多源异构告警（Prometheus/Alertmanager、Loki、K8s Event、黑盒探针、人工报障）归一化为统一的 `NormalizedAlert` 结构，是整条闭环的入口，后续所有 Skill（SK-02 聚合、SK-03 定级）都依赖其输出格式 |
| **输入** | `{rawAlert: {source: string, rawPayload: any, receivedAt: timestamp}, topology: ServiceGraph, suppressRules?: Rule[]}` |
| **输出** | `{normalized: NormalizedAlert, dedupKey: string, severity: P0|P1|P2|P3, affectedServices[], affectedNamespaces[], rawRef: string}` |
| **调用条件** | Sentinel 每收到一条原始告警即调用；告警源 webhook 或轮询触发 |
| **依赖工具** | MCP: `prometheus-mcp`（告警元数据补充）、`k8s-mcp`（Pod/Service/Deployment 元数据关联）、`loki-mcp`（日志告警的上下文补充） |
| **失败处理** | ① 无法解析原始 payload → 保留原始 JSON，标记 `normalized=false` + `parseError`，透传给 Sentinel 不丢弃（不漏报优先）；② 拓扑不可用 → `affectedServices` 标记为空，`confidence=low`；③ 源超时 → 标记数据陈旧但继续处理 |
| **安全边界** | 只读。**告警内容视为不可信输入**（R2 提示注入风险）——归一化时做注入检测（检测 payload 中异常控制字符、伪装的系统指令），检测到则标记 `injectionSuspected=true` 并降级处理 |
| **验证方式** | 用故障数据集（F-01~F-12）的 `expected_alerts` 做回放，验证归一化输出与标注预期一致；注入测试 payload 验证注入检测 |
| **复用价值** | 高。归一化逻辑与运维语义解耦，输入换成工单/风控信号即可用于客服、风控场景的信号标准化 |
| **协同关系** | Sentinel 调用 → 产出 NormalizedAlert → 喂给 SK-02 `alert-correlate` 做聚合 |
| **版本演进** | v1 规则映射 + 拓扑关联；v2 引入注入检测增强；v3 基于历史告警的自适应去重 |

#### SK-09 · `remediation-plan` 修复方案生成

| 要素 | 内容 |
|---|---|
| **用途** | 基于根因结论和匹配到的 Runbook，生成结构化修复方案——含执行步骤、预期效果、回滚路径、爆炸半径预评估，作为 Remediator 的核心决策能力 |
| **输入** | `{rootCause: RootCause, evidenceChain: Evidence[], matchedRunbooks: Runbook[], topology: ServiceGraph, freezeWindow: bool, constraints: {maxRiskLevel: L0|L1|L2|L3|L4}}` |
| **输出** | `{plans: [{action, target, expectedOutcome, rollbackPath, preCheckActions[], postCheckActions[], estimatedRiskLevel: L0-L4, rationale, runbookRef}], recommendedPlanIndex, alternatives}` |
| **调用条件** | Diagnostician 产出根因结论后，Remediator 在 PLANNING 状态强制调用；必须有根因结论（不接受"证据不足"时生成方案） |
| **依赖工具** | MCP: `k8s-mcp`（查目标资源当前状态）、`git-mcp`（读 Runbook）；RAG: Runbook 检索（SK-08 产出）；内部变更冻结策略 API |
| **失败处理** | ① 无匹配 Runbook → 基于根因 + 拓扑生成通用方案，标记 `runbookMatched=false`，`confidence=lower`；② 根因与可用 Runbook 矛盾 → 优先根因，标记 Runbook 可能过时；③ LLM 生成失败 → 退化为纯 Runbook 模板填充（确定性 fallback）；④ 方案涉及 L4 动作 → 只生成建议文本，不进入执行流程（人工处理） |
| **安全边界** | 只读（生成方案，不执行）。**输出的 `estimatedRiskLevel` 仅作参考**——最终等级由确定性规则引擎裁决（Q1），Agent 不能自定最终等级。方案中的命令模板必须经 SK-12 `k8s-safe-exec` 执行，禁止 Agent 绕过 |
| **验证方式** | 用故障数据集回放：验证 F-01 生成的方案是否为"rollout restart"、F-04 是否为"rollout undo"、F-08 是否被规则引擎拦截；人工审批通过率（修复方案采纳率指标） |
| **复用价值** | 高。方案生成范式（根因→方案→回滚→风险标注）可迁移至任何"诊断→处置"场景 |
| **协同关系** | Remediator 调用 → 方案喂给风险引擎（Q9 两阶段管线：SK-10 算爆炸半径 → 规则表定级）→ 定级后决定执行/审批/拒绝 |
| **版本演进** | v1 Runbook 模板 + LLM 填充；v2 引入历史处置成功率排序方案；v3 基于反馈自动优化方案模板 |

#### SK-02 · `alert-correlate` 告警聚合与降噪

| 要素 | 内容 |
|---|---|
| **用途** | 将时间窗内的多源告警按时间/空间/拓扑因果三维聚类，识别噪声与衍生告警，收敛为最小事件集 |
| **输入** | `{alerts: NormalizedAlert[], window: duration, topology: ServiceGraph, suppressRules: Rule[]}` |
| **输出** | `{incidents: Incident[], clusters: AlertCluster[], suppressed: {alert, reason}[], confidence: float}` |
| **调用条件** | 时间窗内新告警数 ≥ 2，或单条告警级别 ≥ P1；Sentinel 每 30s 触发一次滚动聚合 |
| **依赖工具** | MCP: `prometheus-mcp`（读取告警与指标）、`k8s-mcp`（拓扑元数据）、`alertmanager-mcp`（静默规则） |
| **失败处理** | ① 拓扑数据不可用 → 降级为纯时间窗聚类，置信度标记为 low；② 聚类超时 → 透传原始告警（不漏报优先）；③ 聚类置信度 < 0.6 → 拆分为独立事件而非强行合并（宁可多报不可错并） |
| **安全边界** | 只读。抑制告警仅做标记 + 创建带 TTL（默认 30min）的静默，**永不删除原始告警记录**；P0 级告警不可被自动抑制 |
| **验证方式** | 用历史真实故障数据集做离线回放，评估聚合准确率（是否把同一故障的告警归到一起）与漏并率；配套单测覆盖边界场景 |
| **复用价值** | 高。聚合算法与运维语义解耦，输入换成工单/风控信号即可用于客服、风控场景的信号降噪 |
| **协同关系** | Sentinel 调用 → 产出 Incident → 交给 Commander 启动状态机 |
| **版本演进** | v1 规则+时间窗；v2 引入拓扑因果图；v3 基于历史标注数据的学习型聚合 |

#### SK-07 · `rca-hypothesis-rank` 根因假设生成与排序

| 要素 | 内容 |
|---|---|
| **用途** | 基于多源证据生成候选根因假设，按贝叶斯式置信度排序，并为每条假设附支撑证据、反驳证据与验证方法 |
| **输入** | `{incident: Incident, evidence: EvidenceBundle, topology: ServiceGraph, changes: ChangeRecord[], similarCases: HistoricalIncident[]}` |
| **输出** | `{hypotheses: [{description, confidence, supportingEvidence[], contradictingEvidence[], verificationMethod, suggestedRunbook}], overallConfidence, needHumanFlag}` |
| **调用条件** | Incident 进入 DIAGNOSING 状态且 `evidence-collect` 已返回完整证据包 |
| **依赖工具** | MCP: `prometheus-mcp` / `loki-mcp` / `k8s-mcp` / `git-mcp`；RAG: 历史事件向量库、Runbook 库 |
| **失败处理** | ① 全部假设置信度 < 0.5 → 输出「证据不足」并置 `needHumanFlag=true`，附完整证据包供人工快速判断；② 证据相互矛盾 → 并列输出矛盾点，不强行收敛；③ LLM 调用失败 → 退化为纯规则匹配（历史相似事件 Top-3） |
| **安全边界** | 只读，不产生任何变更。**禁止在无证据引用的情况下输出根因**（每条假设必须可追溯到具体指标/日志/变更记录）；输出中的日志片段强制 PII 脱敏 |
| **验证方式** | 用历史事故数据集评估 Top-1/Top-3 命中率；人工标注抽检；线上以「人工是否推翻结论」作为持续反馈信号 |
| **复用价值** | 极高。「证据 → 假设 → 排序 → 验证方法」是通用推理骨架，可直接复用于客服疑难定位、风控欺诈归因，只需替换证据 Schema |
| **协同关系** | Diagnostician 调用 → 结论进 Room → Commander 判定是否进入 PLANNING → Remediator 消费 `suggestedRunbook` |
| **版本演进** | v1 LLM + 规则混合；v2 引入因果图推断；v3 结合线上反馈做置信度校准 |

#### SK-10 · `blast-radius-eval` 爆炸半径评估（v1.1 重构）

> **v1.1 修订（对应第 1 问）**：原契约让本 Skill 输出 `estimatedRiskLevel: L0-L4`，等于让一个 LLM 给动作自定风险等级，与"风险不由 Agent 自评"的立论矛盾。重构为：**本 Skill 只负责把爆炸半径数据算清楚，不再下等级结论**；最终等级由 §7.5 的确定性规则表硬裁定。

| 要素 | 内容 |
|---|---|
| **用途** | 评估一个待执行动作的影响面，输出结构化风险画像，**作为确定性风险引擎的输入数据** |
| **输入** | `{action: RemediationAction, topology: ServiceGraph, currentTraffic: TrafficSnapshot, slo: SLODefinition[], freezeWindow: bool}` |
| **输出** | `{affectedServices[], affectedInstanceRatio, downstreamImpact[], reversible: bool, rollbackCost, rationale}`（**不再含等级字段**） |
| **调用条件** | Remediator 生成方案后、提交风险引擎前**强制调用**，不可跳过 |
| **依赖工具** | MCP: `k8s-mcp`（副本数、拓扑）、`prometheus-mcp`（实时流量与 SLO）、内部变更冻结策略 API |
| **失败处理** | ① 拓扑或流量数据缺失 → **保守估计，向上取一级风险**（fail-safe 而非 fail-open）；② 调用超时 → 该动作按 L3 处理（需人工审批）；③ 任何异常路径都不得让动作被低估风险 |
| **安全边界** | 只读。**其输出仅作为风险引擎的输入数据，不能由 Agent 自行采信或定级**；风险等级最终由确定性规则查表裁决，Agent 无权覆盖 |
| **验证方式** | 用历史变更记录回放，对比人工评估的影响面；红队测试构造「看似安全实则高危」的动作，验证规则表仍判 L3/L4 |
| **复用价值** | 高。可独立用于 CI/CD 发布卡点、变更审批系统，脱离 Argus 单独使用 |
| **协同关系** | Remediator 调用 → 产出喂给确定性风险引擎裁决 → Commander 决定是否发起审批 |
| **版本演进** | v1 拓扑+流量规则；v2 引入历史变更事故率先验；v3 依赖图传播模拟 |

#### SK-12 · `k8s-safe-exec` K8s 安全执行

| 要素 | 内容 |
|---|---|
| **用途** | 对 K8s 变更操作的统一安全封装层：幂等保证、前置校验、快照绑定、干跑预演、执行、结果确认 |
| **输入** | `{action, target, approvalToken?, snapshotId, dryRunFirst: bool, idempotencyKey}` |
| **输出** | `{success, executedCommands[], beforeAfterDiff, snapshotId, auditRecordId, duration}` |
| **调用条件** | 风险等级已由确定性规则表裁定；L2+ 必须已完成 `change-snapshot`；L3 必须携带有效 `approvalToken`；**执行前必须持 Broker 发放的短期令牌** |
| **依赖工具** | MCP: `k8s-mcp`（经 K8s 凭证 Broker，真实凭据不落 Agent） |
| **失败处理** | ① 前置校验不通过 → 拒绝执行并返回具体原因；② dry-run 结果与预期不符 → 中止；③ 执行中失败 → 自动触发 `rollback-execute` 恢复至快照；④ 幂等键重复 → 直接返回上次结果，不重复执行；⑤ approvalToken 过期 → 拒绝，重新走审批；⑥ Broker 拒发令牌（L4/未知）→ 拒绝执行 |
| **安全边界** | **本 Skill 是所有生产变更的唯一出口**（Agent 不允许绕过它直接调 kubectl）。L4 动作清单在此硬编码拦截并**在 Broker 侧二次拦截**；所有执行强制审计留痕；令牌单次任务有效 |
| **验证方式** | 混沌测试环境全动作覆盖测试；幂等性测试（重复调用不产生副作用）；越权测试（尝试执行 L4 动作必须被拒） |
| **复用价值** | 极高。「审批令牌 + 快照 + 幂等 + 干跑 + 自动回滚」的执行封装范式可迁移到任何需要安全执行的系统（数据库运维、云资源变更、CI/CD） |
| **协同关系** | Remediator 唯一的执行入口；执行记录 → Validator 验证依据 → Scribe 复盘素材 |
| **版本演进** | v1 核心动作集；v2 支持批量原子操作；v3 Operator 化 |

#### SK-14 · `slo-verify` 服务恢复验证

| 要素 | 内容 |
|---|---|
| **用途** | 独立判定服务是否真正恢复：SLO 指标回归 + 原始告警消解 + 稳定观察期守候，三项全过才算恢复 |
| **输入** | `{incident, remediationRecord, sloDefinitions[], baselineSnapshot, observeWindow: duration}` |
| **输出** | `{verdict: PASS/FAIL/OBSERVING, sloResults[], resolvedAlerts[], residualAlerts[], evidence[], recommendation}` |
| **调用条件** | Remediator 执行完成后**强制调用**；OBSERVING 期内按固定间隔轮询复检 |
| **依赖工具** | MCP: `prometheus-mcp` / `loki-mcp` / `alertmanager-mcp`，**使用与 Remediator 独立的数据通道** |
| **失败处理** | ① 数据不足以判定 → 判定为 FAIL（保守），触发人工升级；② SLO 定义缺失 → 退化为「原始告警是否消解 + 关键黄金指标是否回归基线」；③ 观察期内出现新告警 → 立即判定 FAIL 并请求回滚；④ 验证本身超时 → FAIL |
| **安全边界** | 严格只读。**不得复用 Remediator 提供的任何数据作为验证依据**（杜绝自证）；**无权直接执行回滚**，只能向 Commander 提出回滚请求，由 Remediator 执行（保持执行/验证职责分离） |
| **验证方式** | 注入「假性恢复」场景（指标短暂回升后再次劣化）检验观察期机制有效性；混沌工程验证 |
| **复用价值** | 高。可独立用于灰度发布验证、变更后健康检查、容量变更验证 |
| **协同关系** | Commander 触发 → 结论决定进入 OBSERVING/CLOSED 或 ROLLING_BACK |
| **版本演进** | v1 阈值判定；v2 引入统计显著性检验；v3 自适应观察期时长 |

#### SK-17 · `knowledge-distill` 知识蒸馏

| 要素 | 内容 |
|---|---|
| **用途** | 把一次事故的完整处置过程蒸馏为可复用知识资产：新增/更新 Runbook、优化 Skill 参数、补充告警抑制规则、更新拓扑因果关系、**生成规则表候选补丁** |
| **输入** | `{postmortem, timeline, allAgentOutputs, humanInterventions[], existingKnowledgeBase}` |
| **输出** | `{runbookProposals[], skillImprovementProposals[], newSuppressRules[], topologyUpdates[], ruleTableCandidates[], similarCaseLinks[], prUrl}` |
| **调用条件** | Incident 进入 REVIEWING 状态且复盘报告已生成 |

| **安全边界** | **只能创建 PR，无合并权限** —— 知识资产与规则变更必须经人工评审（**绝不自动生效**）。复盘报告对事不对人，禁止归因到具体个人。写入前 PII 脱敏 |

| **协同关系** | Scribe 调用 → 知识库/规则表更新 → 经 §5 显式回路反哺 SK-08 `runbook-retrieve`、SK-07 历史案例检索与根因定位 |
| **版本演进** | v1 模板化生成；v2 冲突检测与合并建议；v3 基于采纳反馈的自我优化 |

## 9. 工具集成：MCP 契约

MCP 承担工具连接层，Skill 承担能力抽象层。所有外部系统访问必须经 MCP，禁止 Agent 直连。

| MCP Server | 连接目标 | 主要能力 | 权限范围 | 鉴权 | 失败降级 |
|---|---|---|---|---|---|
| `prometheus-mcp` | Prometheus / Thanos | instant/range query、告警查询、规则查询 | 只读 | Higress 网关注入 Bearer（代持 API Key） | 降级至缓存快照，标记数据陈旧 |
| `loki-mcp` | Loki | LogQL 查询、日志模式统计 | 只读 | Higress 网关注入 | 限流退避重试 3 次 |
| `k8s-mcp` | Kubernetes API | **读**：get/list/watch 全资源；**写**：白名单动作，按 Agent SA 隔离 | 分角色 RBAC，写权限仅 Remediator | **K8s 凭证 Broker 短期令牌**（真实凭据不落 Agent，Broker 侧按规则表 + 审批二次拦截） | 写失败自动回滚，读失败降级 |
| `alertmanager-mcp` | Alertmanager | 告警查询、创建带 TTL 静默 | 读 + 受限写（仅静默） | Higress 网关注入 | 静默失败不阻塞主流程 |
| `git-mcp` | Git 仓库 | 变更记录查询、Runbook 读取、创建 PR | 读 + PR 创建（无合并权限） | Deploy Key / PAT，Higress 持有 | 降级为只读 |
| `ticket-mcp` | 工单系统 | 事件工单创建/更新/关闭 | 读写工单 | Higress 网关注入 | 本地队列缓冲，恢复后补写 |
| `im-mcp` | Matrix / 企业 IM | 通知推送、审批卡片 | 写消息 | Higress 网关注入 | 多通道兜底（IM 失败转短信/电话） |

**统一契约要求**（所有 MCP Server 必须满足）：
- 输入输出 Schema 用 JSON Schema 显式声明，纳入版本管理
- 所有写操作必须支持幂等键
- 统一错误码规范，区分「可重试」与「不可重试」
- 每次调用产生审计记录：调用方 Agent、时间、参数、返回、耗时、Trace ID
- 权限范围在 Worker CRD 中声明式配置，运行时不可提权
- 超时与重试策略可配置，默认指数退避

## 10. 上下文与记忆体系

> 赛道要求：「从 Agent 记忆存储、知识库 RAG、共享状态管理、轨迹可观测 4 项能力中至少实现 2 项」。本方案**四项全实现**。

| 能力 | 实现方案 | 说明 |
|---|---|---|
| **① 知识库 RAG** | **PostgreSQL + pgvector（自托管）** | 三个知识库：Runbook 库（处置手册）、历史事件库（含处置过程与结果）、架构知识库（服务依赖、SLO 定义、变更规范）。检索时做证据对齐，结果必须附来源引用 |
| **② Agent 记忆存储** | Hermes 持久记忆 + PostgreSQL 结构化记忆 | 短期：当前 Incident 的 Room 上下文；长期：每个 Agent 的领域经验（如 Diagnostician 记住「服务 A 的 CPU 尖刺通常是定时任务导致」） |
| **③ 共享状态管理** | `Incident` CRD status + Redis + MinIO | 状态机状态存 CR status（K8s 原生一致性）；高频中间态存 Redis；大对象证据存 MinIO，Room 内只传句柄 |
| **④ 轨迹可观测** | AgentLoop / LoongSuite，遵循 OpenTelemetry GenAI 语义规范 | 见第 11 节 |

**上下文传递的关键设计**：所有 Agent 间消息采用**双写格式** —— 结构化 JSON payload（供 Agent 精确消费）+ 自然语言摘要（供人类在 Room 内直接读懂）。这保证了「人类全程可见、随时可介入」不是一句口号。

## 11. 可观测与执行证据

### 11.1 观测数据

| 类型 | 采集内容 | 用途 |
|---|---|---|
| **Trace** | Skill 调用、MCP 工具调用、RAG 检索、LLM 推理全链路，遵循 OTel GenAI 语义规范 | 事后回放、性能瓶颈定位、成本归因 |
| **Metrics** | 各阶段耗时、Skill 成功率、Token 消耗、审批等待时长、自主闭环率 | 效能量化、SLO 监控、成本控制 |
| **Log** | Agent 决策日志（含推理摘要）、工具调用原文、人工干预记录 | 审计、调试、复盘素材 |

### 11.2 执行证据包

每起 Incident 关闭时自动归档一个**可独立审计的证据包**：

```
incident-{id}/
├── timeline.json          # 完整时间线（机器可读）
├── postmortem.md          # 复盘报告（人类可读）
├── trace.otlp             # 全链路 Trace
├── agent-messages.jsonl   # Room 内完整消息流（PII 已脱敏）
├── evidence/              # 诊断证据：指标快照、日志切片、拓扑图
├── changes/               # 变更前后 YAML diff、快照句柄
├── approvals/             # 审批记录（谁、何时、批了什么、依据）
├── rule-table-decisions/  # 风险引擎裁定记录（命中规则表哪一条）
└── verification/          # 验证数据与判定依据
```

这个证据包的设计目标：**任何一个没参与过这起事故的人，仅凭证据包就能完整复现整个决策过程并判断其是否合理**。

### 11.3 Agent 效果评估

基于观测数据做离线评估：根因命中率、方案采纳率、误修复率、单事件成本。**所有指标在「同一份固定标注数据集」上计算**（见 §14.3），每次 Agent/Skill/Prompt 变更前跑一遍回归，防止能力退化，也杜绝"靠不执行刷单边指标"的退化均衡。

## 14. 指标体系

### 14.1 北极星指标

> **自主闭环率（Autonomous Resolution Rate）** = 无人工介入完成「检测 → 定位 → 修复 → 验证通过」的事件数 / 总有效事件数

选它的理由：这是唯一同时衡量了「降噪准不准、定位对不对、修复行不行、验证严不严」的复合指标。任何一环偷工减料，这个数都会掉。目标：Demo 环境 L1/L2 类故障 ≥ 70%。

**必须与对称护栏同看（v1.1 强化）**：单看自主闭环率会诱导两种退化——① 冒进执行高风险动作（误修复）；② 永远不执行（应执未执）。因此必须与下方「护栏指标」**联合约束**，且所有指标在**同一固定标注数据集**上计算，杜绝单边刷分。

### 14.2 驱动指标

| 指标 | 定义 | 基线 | 目标 |
|---|---|---|---|
| 告警降噪率 | 1 - 产生的 Incident 数 / 原始告警数 | — | ≥ 90% |
| 事件聚合准确率 | 同一故障告警被正确归并的比例 | — | ≥ 85% |
| MTTD | 故障发生到 Incident 创建 | 人工基线待测 | 下降 ≥ 50% |
| MTTR | 故障发生到验证通过 | 人工基线待测 | 下降 ≥ 40% |
| 根因 Top-1 命中率 | 首位假设即为真实根因的比例 | — | ≥ 60% |
| 根因 Top-3 命中率 | 真实根因在前三位的比例 | — | ≥ 85% |
| 修复方案采纳率 | 人工审批通过 / 提交审批总数 | — | ≥ 80% |
| 一次修复成功率 | 首次执行即通过验证 | — | ≥ 75% |
| 知识转化率 | 生成的 Runbook PR 被合并的比例 | — | ≥ 30% |

### 14.3 健康与护栏指标

> **v1.1 修订（对应第 4 问）**：原护栏是单向的（只防冒进），"最优解"可以是永远不执行——那样护栏全绿但闭环率≈0，系统退化成摆设。修订为**对称护栏 + 可操作定义 + 固定基准**。

| 指标 | 说明 | 红线 / 目标 |
|---|---|---|
| **误修复率** | **可操作定义**：修复后观察期内 SLO 再劣化 / 触发回滚 / 引发二次故障的比例（由证据包自动判定，非主观） | ≤ 2%（超线自动降级为只建议模式） |
| **回滚率** | 需要回滚的执行占比 | ≤ 10% |
| **二次故障率** | 修复引发新故障的比例 | ≤ 1%（超线立即熔断） |
| **人工推翻率** | 人工否决 Agent 根因结论的比例 | ≤ 20%（超线说明定位能力不达标） |
| **误抑制率** | **可操作定义**：被抑制告警中后续被确认为真实故障的比例（由证据包自动判定） | ≤ 0.5%（最危险指标，漏报比误报严重） |
| **过度保守率 / 应执未执率**（v1.1 新增·对称护栏） | 本可自主解决（命中 L1/L2 或已有 Runbook）却升级人工 / 被默认拒绝的比例 | ≤ 15%（超线说明系统过度保守、退化成摆设） |
| **夜间人工打扰次数** | 22:00–08:00 需人工介入的次数 | 相对基线下降 ≥ 60% |
| **审批等待时长** | 审批请求到响应的时间 | P95 ≤ 10min |
| **单事件 Token 成本** | 端到端 LLM 成本 | ≤ 0.5 元 |
| **Agent 决策延迟** | 各阶段 P95 耗时 | 见非功能需求 |

**固定评估基准（v1.1 新增）**：上述所有指标（含闭环率与对称护栏）在**同一份固定标注故障数据集**上计算。闭环率涨但护栏破了立刻可见，任何单边优化都无法刷分。数据集来源见 §18 T1。

## 附录 A：术语表

| 术语 | 定义 |
|---|---|
| Incident | 经聚合去重后的一起故障事件，本系统的核心对象 |
| 自主闭环 | 无人工介入完成检测→定位→修复→验证通过的完整过程 |
| 爆炸半径 | 一个动作可能影响的服务与实例范围 |
| 分级自治 | 按动作风险等级差异化授予 Agent 执行权限的策略 |
| 假性恢复 | 指标短暂回归正常后再次劣化的现象 |
| 三层防御纵深 | K8s 凭证 Broker + RBAC 最小权限 + 确定性风险分级引擎/审批的叠加防护 |
| 确定性风险分级引擎 | 声明式规则查表，对动作定级（L0–L4 + 未知默认拒绝），Agent 零覆盖权 |
| 人类在环（Human-in-the-loop） | 高风险与未知动作必须人工审批/评审，人是守门者而非被替代者 |
| Runbook | 针对特定故障类型的标准处置手册 |
| MTTD / MTTR | 平均检测时长 / 平均恢复时长 |
| SLO | 服务等级目标 |
